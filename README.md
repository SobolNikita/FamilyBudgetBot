# Семейный бюджет

Учёт расходов одной семьи: Telegram-бот на естественном языке и открытая веб-панель. Go, PostgreSQL, React, TypeScript. Панель и REST API работают без авторизации, как согласовано: любой посетитель может просматривать и изменять все расходы. В Telegram участник работает только со своими записями.

[Изменения и проверки версии 0.2.0](docs/releases/0.2.0.md).

## Исправления согласованности диалога

Продолжение списка в боте привязано к версии расходов участника. Если между страницами запись создана, изменена или удалена, бот просит начать просмотр заново: изменившийся набор не выдаётся за полностью просмотренный. Проверка версии и чтение страницы используют один SQL-снимок. Веб-пагинация сохраняет переход по номеру страницы.

Перед планированием сохранённые ссылки диалога сверяются с БД: удалённые и переданные другому участнику расходы исключаются, изменённые обновляются; противоречивая история очищается. Подтверждение удаления сохраняет исходную версию записи. Даты реплик передаются модели для уточнений после полуночи.

Форма редактирования при конфликте сохраняет черновик и предлагает загрузить актуальную запись. Пользователь может принять текущие данные либо проверить свой черновик перед новой записью. После потери ответа PUT сначала проверяется результат, повторное изменение автоматически не отправляется. Бот понимает «да, конечно», «да, удали его» и «не удаляй»; новая покупка во время подтверждения не теряется молча — бот объясняет, что её нужно прислать после отмены.

## Удаление участника

В панели нажмите «Управление участниками», выберите человека и подтвердите «Удалить участника и расходы». Можно удалить в том числе последнего участника. Общие итоги пересчитаются; выбранный фильтр участника сбросится на всю семью.

В одной транзакции удаляются **все расходы, которые на момент операции принадлежат этому участнику**, его состояние диалога, имя и незавершённая регистрация. Записи, ранее переданные другому участнику, остаются у нового владельца. Связанные сохранённые ответы веб-создания очищаются и помечаются отозванными: повтор старого `Idempotency-Key` возвращает `410`, даже после восстановления доступа. Это касается и ключей исходного владельца, если расход позднее был передан удаляемому участнику.

В `users` остаётся минимальная служебная запись: Telegram ID, дата удаления, версия членства и технические счётчики/временные отметки. Имя очищается. В `telegram_updates` сохраняются ID обработанных обновлений и технические метаданные для дедупликации, но текст входящих сообщений и ответы удаляемого участника стираются, ожидающая обработка/доставка завершается без исполнения. Эти транспортные отметки очищаются обычным механизмом через 7 дней. Ключи и хеши отозванных веб-запросов остаются без срока истечения, без сохранённых расходов в ответе. Диалоги других участников с явными ссылками на затронутые записи сбрасываются, чтобы не предлагать удалённые расходы.

Удалённый участник не может автоматически вступить снова: на новое сообщение бот отвечает, что доступ удалён, без вызова LLM и сохранения присланного текста. В разделе «Удалённые участники» доступ можно восстановить по Telegram ID. Старые расходы, имя и диалог не возвращаются; человек должен представиться заново. Ожидающие ответы об удалённом доступе при восстановлении отменяются. Начальная регистрация остальных новых пользователей остаётся открытой, как в исходной версии; поддержка нескольких семей не добавляется.

Для границы удаления используется транзакционная advisory-блокировка: обычные записи и доставка берут shared lock, удаление/восстановление — exclusive. Во время обращения к LLM блокировка не удерживается. Ответ модели, пришедший после удаления, увидит завершённое обновление и не сможет вернуть расход или историю. Доставка повторно читает запись под блокировкой. Если отправка Telegram уже началась, удаление дожидается её завершения; уже принятые Telegram сообщения не отзываются. Таймаут удаления можно безопасно обработать повтором **того же ID и версии**. Повтор старого удаления после восстановления даст `409` и не удалит участника заново.

Удаление не чистит уже полученные сообщения в Telegram, выгруженные файлы, журналы внешних сервисов и резервные копии БД. Для эксплуатации с такими копиями их срок хранения задаётся отдельно. API панели, включая управление участниками, по ТЗ не имеет авторизации.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/users` | Зарегистрированные активные участники с `version` |
| GET | `/api/users/removed` | Telegram ID, версия и дата удаления; без имени |
| DELETE | `/api/users/{id}?version=N` | Удалить участника и его данные; повтор той же операции безопасен |
| POST | `/api/users/{id}/restore?version=N` | Разрешить регистрацию заново; данные не восстанавливает |
| GET | `/api/expenses/{id}` | Получить актуальную запись для разрешения конфликта веб-формы |

Миграции `000005` и `000006` применяются обычным сервисом `migrate` в Compose. Перед обновлением выполните резервное копирование. Откат схемы не восстанавливает удалённые данные; восстановление из резервной копии — отдельная операция. Проверки удаления и восстановления включены в PostgreSQL-тесты, браузерную приёмку и Compose smoke test.

## Запуск

В верхней панели доступен переключатель светлой и тёмной темы с иконками солнца и луны. Выбор сохраняется в `localStorage` этого браузера и применяется при следующем открытии, в том числе после его перезапуска. Инициализация загружается отдельным скриптом, разрешённым политикой безопасности сервера, до отображения страницы. По умолчанию тема светлая; открытые вкладки синхронизируют выбор. Очистка данных сайта сбрасывает настройку, а в приватном режиме она может не сохраняться после закрытия окна.

Нужны Docker Engine и Docker Compose v2.

По умолчанию приложение настроено для России: российские рубли (`FAMILY_CURRENCY=RUB`), московское время (`FAMILY_TIMEZONE=Europe/Moscow`) и русский формат чисел и дат. Для другого региона России можно указать соответствующий часовой пояс IANA, например `Asia/Yekaterinburg`. Часовой пояс определяет семейную дату, понимание слов «сегодня» и «вчера», а также время логов приложения в Compose.

1. Скопируйте `.env.example` в `.env`.
2. Замените `POSTGRES_PASSWORD`. Для регистрации участников включите бота и настройте Telegram/LLM по разделу ниже.
3. Выполните:

```sh
docker compose up --build -d
```

Панель: `http://localhost:8080`. На сервере — `http://<адрес-сервера>:8080`, если порт разрешён в сетевых настройках. Приложение слушает все интерфейсы; SSH-туннель не нужен. Для домена и HTTPS можно поставить внешний reverse proxy.

Выбранный участник, категория, даты и страница списка сохраняются в адресной строке. Перезагрузка, закладка или открытие скопированной ссылки восстанавливают этот вид; кнопки браузера «Назад/Вперёд» переключают предыдущие наборы фильтров. «Сбросить» сохраняет режим за всё время даже после обновления. Если записи удалены и сохранённая страница больше не существует, открывается последняя доступная страница. Несохранённые формы добавления и редактирования не восстанавливаются.

Пункт «Общие траты» показывает расходы всей семьи и расположен отдельно, выше раздела «Участники». Под заголовком «Участники» находятся только члены семьи; на телефоне их список прокручивается горизонтально. При переключении сохраняются даты и категория, а список начинается с первой страницы.

Под списком расходов можно нажать номер страницы или ввести его в поле «Страница» и нажать «Перейти» (либо Enter). Выбранные участник, даты и категория сохраняются; номер страницы восстанавливается после обновления и при переходах назад/вперёд в браузере.

На телефонах до 700 px расходы отображаются карточками без горизонтальной прокрутки; фильтры, страницы и действия доступны крупными кнопками. Формы открываются в одну колонку с внутренней прокруткой. На широких экранах сохраняется таблица.

Compose запускает PostgreSQL, применяет миграции отдельным контейнером и запускает приложение. Фронтенд собирается внутри Docker. База не публикует порт наружу, данные сохраняются в Docker volume.

```sh
docker compose logs -f app
docker compose down
```

`docker compose down` сохраняет данные. Не добавляйте `-v`, если базу требуется сохранить.

## Telegram и LLM

Панель запускается без внешних ключей с `BOT_ENABLED=false`. Для бота укажите в `.env`:

```dotenv
BOT_ENABLED=true
TELEGRAM_BOT_TOKEN=<токен от BotFather>
LLM_BASE_URL=https://api.openai.com/v1
LLM_API_KEY=<ключ провайдера>
LLM_MODEL=<модель с поддержкой Chat Completions tool calling>
LLM_TIMEOUT=20s
```

Поддерживается OpenAI-совместимый протокол `/chat/completions` с `tools`, `tool_choice` и `parallel_tool_calls`. `LLM_BASE_URL` включает `/v1`, но не `/chat/completions`. Для локального провайдера ключ может быть пустым. Модель выбирается явно; реальный LLM не вызывается в тестах.

После изменения `.env` выполните `docker compose up -d --force-recreate app`. Боту не нужен webhook: работает long polling. Для токена не должен быть установлен webhook или запущен другой бот-получатель обновлений.

Каждое сохранённое сообщение получает отдельный ответ, привязанный к исходному сообщению Telegram. Пока запрос выполняется, бот пишет «Сообщение принято…», затем заменяет этот текст результатом или понятной ошибкой. Быстрые запросы могут сразу получить итоговый ответ. Подтверждения отправляются независимо от LLM. До четырёх пользователей обрабатываются параллельно, внутри каждого диалога порядок сохраняется. Доставка чередует пользователей и учитывает возраст попыток: новые подтверждения не вытесняют готовый результат бесконечно. Редактирование ответа не создаёт новое сообщение и может не вызвать новое уведомление Telegram.

`LLM_TIMEOUT` ограничивает один запрос к модели, включая чтение ответа: по умолчанию `20s`, допустимо от `1s` до `2m`. При ошибке LLM повторных скрытых попыток нет: бот сохраняет итоговую ошибку и не изменяет расходы. При 401/403/404 следующие вызовы провайдера приостанавливаются на 5 минут, при 429 — на минуту, при ошибках сети/5xx — на 5 секунд; пользователи получают соответствующую ошибку. После изменения ключа перезапустите приложение. Если сообщение ожидало начала обработки более часа, оно не исполняется, а получает предложение прислать запрос заново. При остановке приложения незавершённые сообщения остаются в PostgreSQL.

В очереди допускается до 20 ожидающих сообщений одного пользователя. Следующие принятые сообщения получают явный отказ без изменения расходов. При 1000 активных недоставленных сообщений приём новых обновлений приостанавливается до освобождения места; offset не продвигается за несохранённый update. Telegram хранит ещё не принятые обновления ограниченное время, поэтому длительная перегрузка требует вмешательства оператора.

### Диагностика LLM и доставки

В `docker compose logs -f app` ошибки LLM содержат `update_id`, безопасный `code`, `http_status` и `duration_ms`. Тела ответов провайдера, ключи, адреса запросов и текст расходов не логируются. Успешные LLM-запросы также записывают длительность.

| Код | Что проверить |
| --- | --- |
| `authentication` / HTTP 401 | Ключ `LLM_API_KEY` |
| `permission` / HTTP 403 | Права ключа, доступ к модели и ограничения провайдера |
| `model_or_endpoint` / HTTP 404 | `LLM_MODEL` и `LLM_BASE_URL` |
| `rate_limit` / HTTP 429 | Частоту запросов, квоту и баланс провайдера |
| `timeout` | Скорость модели, сеть и `LLM_TIMEOUT` |
| `dns`, `tls`, `connection` | DNS, сертификаты, сеть и прокси сервера |
| `unavailable` | Доступность провайдера; обычно HTTP 5xx |
| `request`, `invalid_response` | Совместимость модели с tool calling и формат ответа |

В `telegram_updates.last_error` сохраняется код обработки (например, `llm_timeout`), даже после доставки ошибки пользователю. `delivery_error` хранит последнюю ошибку доставки отдельно, `send_attempts` — число неудачных попыток текущего этапа, `reply_message_id` — ID ответа бота. Миграция `000003_reply_delivery` добавляет эти сведения без удаления расходов.

При первом сообщении в личном чате бот спрашивает имя. Пришлите имя (от 1 до 80 символов), затем подтвердите предложенное имя ответом «да» или отклоните ответом «нет». Только после подтверждения участник появляется в панели. Это защищает от случайной регистрации с именем «такси 10» при отправке пачки сообщений. До завершения регистрации расходы не создаются; расходы из сообщений знакомства нужно прислать заново. Регистрация не вызывает LLM и сохраняется при перезапуске приложения. Чтобы изменить имя, напишите «изменить имя», «хочу поменять имя» или попросите об этом своими словами. Бот спросит новое имя и попросит подтвердить его. До ответа «да» прежнее имя сохраняется; «отмена» завершает смену имени. Команда `/name` больше не запускает смену имени.

После знакомства участники пишут боту в личном чате:

- `кофе 350`
- `Чипсы 5 Йогурт 8` — две отдельные записи; можно также разделять покупки запятыми или переносами строк.
- `такси 1200 вчера`
- `сколько потратил на еду в этом месяце`
- `покажи расходы за неделю`
- `последнее было не 350, а 450`
- `удали такси` → бот уточняет запись или просит подтвердить удаление текстом `да` / `нет`.

За одно сообщение можно добавить от 1 до 20 расходов: бот сохраняет весь список одной транзакцией и перечисляет созданные записи в ответе. При ошибке любой позиции весь список откатывается; при неоднозначности бот должен уточнить данные до сохранения. Следующее «последнее» относится к последней позиции списка. Изменение и удаление по-прежнему выполняются для одной записи за сообщение.

Если нужной записи нет среди последних 30 или ранее показанных расходов, сначала запросите её список с фильтром. Контекст действует 30 минут; повторное подтверждение после его истечения не удаляет расход. Команды и кнопки для работы не нужны; `/start` показывает подсказку.

Для «покажи ещё» сервер сохраняет фильтры последнего списка и следующую позицию отдельно от четырёх последних реплик. Продолжение работает после длинного диалога и перезапуска приложения, пока действует контекст. Модель выбирает `continue_expenses`, а сервер использует сохранённые параметры. Новый явно заданный период начинает новый список. Если контекст истёк или список закончился, бот сообщает об этом. Как и обычная пагинация по смещению, последовательность страниц может меняться при одновременном добавлении и удалении расходов через веб-панель.

Участники хранятся только в `users`; список ID в `.env` не нужен. Зарегистрироваться может любой написавший боту. Владельцем расхода остаётся Telegram ID отправителя; одинаковые имена допустимы. При обновлении проекта существующие участники и расходы сохраняются. В открытой панели нажмите «Обновить», чтобы увидеть новых участников; до первого знакомства с ботом список пуст.

В Telegram доступны только собственные расходы. Запрос «Сколько потратила Ева за неделю» от Никиты должен получать «Доступ запрещён», а не отчёт Никиты. Модель получает имя только отправителя и явно определяет владельца запроса (`subject`); для другого человека или всей семьи сервер возвращает фиксированный отказ без выполнения операции. Если владелец неясен, бот уточняет его; отсутствие `subject` не трактуется как запрос своих расходов. Семантический разбор остаётся задачей LLM, а изоляция данных по Telegram ID независимо обеспечивается сервером. Упоминание человека как получателя подарка не означает запрос к его расходам. Веб-панель этим ограничением не меняется.

Валюта `FAMILY_CURRENCY` одна для всей базы и фиксируется в `budget_settings` при первом запуске после миграции `000004`. При обновлении существующей установки используйте её прежнюю валюту. Дальнейшее несовпадение настройки и БД останавливает запуск: смена валюты требует отдельной миграции сумм, а не переименования настройки. Относительные даты в боте считаются от времени отправки исходного Telegram-сообщения в `FAMILY_TIMEZONE`, включая обработку после полуночи. Время сообщений, принятых до миграции, восстанавливается из `created_at`.

## Тестовые страницы расходов

`scripts/seed-pagination.sql` добавляет 240 расходов существующему участнику (12 страниц по 20 записей). Передайте в `psql` параметры `-v user_id=ID` и `-v spent_at=YYYY-MM-DD`. Комментарии помечены `[pagination-test-v1]`; повторный запуск для того же участника не дублирует записи. Это настоящие записи в выбранной БД: они учитываются в отчётах. Для удаления только этого набора используйте `DELETE FROM expenses WHERE user_id = ID AND comment ~ '^\[pagination-test-v1\] [0-9]{3}$';`, подставив ID участника.

| GET | `/api/expenses` | Расходы: `user_id`, `from`, `to`, `category`, `search`, `limit`, `offset` |
| POST | `/api/expenses` | Создать расход |
| PUT | `/api/expenses/{id}` | Заменить поля расхода с проверкой `version` |
| DELETE | `/api/expenses/{id}?version=1` | Удалить расход с проверкой версии |
| GET | `/api/reports/summary` | Точная сумма и категории с теми же фильтрами |
| GET | `/health/live`, `/health/ready` | Работа процесса и доступность PostgreSQL |
| GET | `/health/bot` | Состояние polling/worker/LLM; 503 при деградации, отдельно от readiness веба |
| GET | `/health/queues` | Размеры и возраст очередей, приостановленная доставка и статистика HTTP-пула БД |

Для `POST /api/expenses` обязателен заголовок `Idempotency-Key`: случайный идентификатор операции из 16–128 букв, цифр, `-` или `_`. При повторе после обрыва связи используйте тот же ключ и те же поля: сервер вернёт исходный результат, даже если расход уже изменён или удалён, и не создаст новую запись. Другие данные с тем же ключом дают 409. Новая намеренная покупка должна иметь новый ключ. Записи ключей сохраняются без автоматического истечения; удаление таблицы `expense_requests` отменяет защиту старых повторов.

Пример тела создания:

```json
{
  "user_id": "123456789",
  "amount": "12.50",
  "category": "еда",
  "spent_at": "2026-10-16",
  "comment": "Кофе"
}
```

ID и суммы в API — строки, чтобы не терять точность JavaScript. При обновлении также передаётся текущая `version`; при конфликте сервер возвращает `409`, при неверных данных — `400`, при отсутствии записи — `404`. Границы периода включительны, размер страницы — до 100 записей. Отчёт считает весь выбранный период независимо от пагинации.

### Приёмка естественного языка

Обычные Go-тесты не обращаются к LLM. Отдельный набор из 16 синтетических примеров проверяет выбранную реальную модель: фразы из ТЗ, «вчера» на границе февраля високосного года, уточнение суммы, неоднозначное удаление, несколько покупок, отказ в чужих расходах, инструкции внутри комментария и продолжение списка после сокращения истории.

Из корня проекта с настроенными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в `.env`:

```sh
node --env-file=.env scripts/check-llm.mjs
```

Нужны Go и Node.js 24. Скрипт вызывает только LLM с вымышленными данными; Telegram и база приложения не используются. Результаты содержат дату, модель, endpoint, хеш системного промпта, ожидаемые и фактические действия. Отчёт сохраняется в `.cache/llm-eval.json`; путь можно задать через `LLM_EVAL_REPORT`. Ключ не записывается в отчёт. Один прогон делает максимум 16 вызовов, с лимитом 30 секунд на вызов и пяти минут на набор. Автоматических повторов нет: ошибка провайдера останавливает дальнейшие вызовы, не превращая пропущенные примеры в успешные.

Набор проверяет семантику предложенных действий; серверное выполнение и изоляцию проверяют обычные тесты. Для текущего месяца/недели допускается верхняя граница «сегодня» либо конец календарного периода. При неоднозначном удалении допустимы уточняющий вопрос или список кандидатов с соответствующим поиском; выбор произвольной записи для удаления не допускается. Один успешный прогон не гарантирует все будущие ответы модели. При изменении модели или промпта приёмку следует повторить; платные вызовы в обычный CI не включены.

Проверка 18 октября 2026 года на `gemini-3.1-flash-lite`: **16 из 16 примеров прошли**. [Полный результат с входами, действиями и хешем промпта](docs/evaluations/llm-2026-10-18.json). По результатам приёмки уточнены инструкции: просьба показать записи не должна заменяться сводкой, а неизвестная сумма требует вопроса, без попытки записать `?` как цену.

Этот отчёт относится к сохранённому в нём хешу промпта. После добавления дат исторических реплик промпт изменён; прежние 16/16 не являются live-проверкой новой версии. Обычные тесты, проверки PostgreSQL и управляемые планировщики не заменяют повторную приёмку выбранной реальной модели.

## Надёжность и данные

Состояния очереди разделяют исполнение и доставку:

| Состояние | Значение | Следующий шаг |
| --- | --- | --- |
| `pending` | Сообщение сохранено, действие ещё не зафиксировано | Обработка или ограниченный повтор |
| `processed` | Результат сохранён: действие выполнено либо сохранён окончательный отказ | Доставка результата |
| `sent` | Доставка результата подтверждена | Очистка через 7 дней |

`reply_message_id` хранит ID уже отправленного подтверждения или результата. Флаг `delivery_suspended` приостанавливает только доставку, не отменяя сохранённые расходы. Старое допустимое значение `failed` сохранено в схеме для совместимости; текущая обработка записывает окончательные ошибки как `processed` с текстом ответа и кодом причины.

Обработка действия, запись расходов и сохранение ответа фиксируются одной транзакцией. Telegram-обновления дедуплицируются по `update_id`; повторная доставка не создаёт расход заново. Для внутренних ошибок обработки остаются 3 попытки, для ошибок LLM — одна. Временные ошибки доставки повторяются с интервалом до 64 секунд и учётом большего `retry_after`. Ошибка 403 приостанавливает доставку в чат, 400 — конкретного недоставляемого ответа. Данные сохраняются для диагностики. Новое входящее сообщение возобновляет приостановленные из-за 403 ответы, пока есть место в активной очереди. Ошибка 401 приостанавливает попытки на минуту и отражается в здоровье бота. Недоставленные ответы не удаляются; доставленные очищаются порциями по 1000 строк после 7 дней хранения. Если подтверждение бота удалено и его нельзя отредактировать, итог отправляется новым ответом.

Абсолютная гарантия мгновенной доставки невозможна: при отключённом сервере, недоступной БД/сети/Telegram или блокировке бота пользователем ответ не может быть отправлен. Гарантия приложения — сохранение принятого сообщения и его результата в PostgreSQL с повторной доставкой после восстановления связи. Если Telegram принял новое сообщение, но соединение оборвалось до получения его ID или сохранения ID в БД, возможен дубль ответа; для редактирования того же ответа повтор безопасен. Действие с расходами при этом не повторяется.

Один координатор бота на базу обеспечивается advisory lock, здоровье его соединения проверяется независимо от LLM. Потеря соединения отменяет текущую работу. До четырёх диалогов исполняются параллельно, внутри пользователя — последовательно; доставка справедливо чередует чаты. В LLM отправляются только данные соответствующего участника. Это схема одного активного координатора, а не распределённая гарантия exactly-once внешних вызовов.

API ограничивает обработку запроса 12 секундами и допускает до 32 одновременных операций. Бот и веб имеют отдельные пулы по 8 соединений. Операции БД, включая ожидание пула, ограничены 10 секундами, rollback — двумя. Остановка HTTP и бота имеет общий бюджет 15 секунд, закрытие пулов — ещё 3; Compose ждёт до 25 секунд. При невозможности остановить runner приложение завершается с ошибкой, чтобы не запускать новые копии поверх зависших работников. При обычном отказе runner перезапускается через 30 секунд, веб остаётся доступным.

`/health/bot` и `/health/queues` предназначены для мониторинга; общая readiness веба не скрывает состояние бота. Приостановленные ответы можно найти запросом `SELECT update_id,user_id,delivery_error FROM telegram_updates WHERE delivery_suspended`. После устранения причины 400 оператор может возобновить конкретный ответ: `UPDATE telegram_updates SET delivery_suspended=false,delivery_next_attempt_at=now() WHERE update_id=ID`. Не очищайте расход или его результат ради повторной доставки.

В `/health/bot` поле `delivery_code` описывает общую ошибку доставки отдельно от `worker_code`, `poll_code` и `llm_code`. Успешная доставка очищает только свой статус; остановленный worker или ошибка LLM при этом остаются видны. Ошибки 400/403 отдельного сообщения/чата отражаются в очереди и не делают весь бот неработоспособным.

Каждый HTTP-ответ содержит сгенерированный сервером `X-Request-ID`. Для необработанного panic в журнал попадают этот ID, метод, путь без query-параметров, тип panic и стек. Значение panic, тело запроса и переданный клиентом request ID не логируются этим обработчиком. Внутренние подробности не возвращаются пользователю.

При пустом поле «По дату» верхняя граница периода отсутствует: будущие даты тоже входят в список и итог. Интерфейс обозначает такой период «без конечной даты».

Форма создания выбирает открытого участника, перечитывает текущую дату при открытии и сохраняет ключ операции при повторе. Если результат сохранения неизвестен, поля блокируются до повтора либо закрытия формы; перед новой операцией обновите список. Клиент ограничивает запрос 15 секундами. При ошибке загрузки итоги предыдущих фильтров скрываются. Количество и строки одной страницы читаются в одном SQL-снимке; отдельная сводка может отражать чуть более новое состояние при конкурентных изменениях.

Резервная копия средствами PostgreSQL (замените имя пользователя/БД, если меняли настройки):

```sh
docker compose exec db pg_dump -U family -d family_expenses -Fc -f /tmp/family.dump
docker compose cp db:/tmp/family.dump ./family.dump
```

Проверка восстановления в отдельную базу:

```sh
docker compose cp ./family.dump db:/tmp/restore.dump
docker compose exec db createdb -U family family_restore_check
docker compose exec db pg_restore -U family -d family_restore_check --no-owner --exit-on-error /tmp/restore.dump
docker compose exec db psql -U family -d family_restore_check -c "SELECT count(*) FROM expenses;"
```

Периодическое копирование и хранение копии вне сервера настраиваются отдельно. Файл дампа содержит семейные данные и не должен попадать в Git.

## Соглашение Git

Сообщения коммитов в формате Conventional Commits: `feat: add expense management`, `fix: prevent duplicate telegram expenses`, `docs: describe deployment`, `test: cover expense isolation`, `chore: update dependencies`.

Ветки: `main` — основная версия, `develop` — интеграция изменений, `feature/*` — новая функциональность, `release/*` — подготовка версии, `hotfix/*` — срочные исправления основной версии.

Начальная история реконструирована из уже существовавших файлов: коммиты группируют готовую работу по подсистемам. Даты коммитов отражают инициализацию репозитория, а не первоначальное время разработки.

Кратко об устройстве проекта: бэкенд на Go, веб-панель на React и TypeScript, база данных PostgreSQL. Telegram-бот использует LLM для разбора сообщений, а веб-панель работает с бэкендом через REST API.
