# 0.2.0 — согласованность расходов и удаление участников

## Изменения

- F1: бот обнаруживает изменение набора между страницами и просит начать просмотр заново, не заявляя о полном просмотре пропущенных записей.
- F2: ссылки диалога сверяются с актуальными расходами; удалённые и переданные записи исключаются. Подтверждение удаления сохраняет исходную версию.
- F3: веб-форма сохраняет черновик при 409, позволяет сверить актуальные данные и проверить результат после потери ответа PUT.
- F4: расширены естественные формулировки подтверждения/отмены удаления; новая покупка во время подтверждения получает явное объяснение.
- Даты исходных реплик передаются в LLM для уточнений после полуночи; старый live-отчёт помечен как исторический.
- Добавлено управление участниками: удаление расходов и истории, блокировка повторной регистрации, восстановление только доступа.
- Незавершённая работа бота и доставка согласованы с удалением. Ключи удалённых операций остаются отозванными после восстановления доступа.
- Форма и модальное окно выделены из App; SQL страницы сделан читаемее, ожидания браузерного harness ограничены по времени.
- Compose собирает общий образ приложения и миграций один раз.

## Обновление

Обычный запуск: `docker compose up --build -d`. Перед обновлением сделайте резервную копию. Новые миграции: `000005_expense_revision`, `000006_member_removal`.

Удаление участника безвозвратно удаляет его текущие расходы. Уже отправленные Telegram-сообщения и резервные копии не очищаются. В БД остаются технические отметки блокировки, дедупликации и отозванных операций. Подробный контракт и REST endpoints описаны в README.

При развёртывании остановите старый экземпляр бота/приложения перед приёмом запросов новой версией. Все активные процессы должны поддерживать блокировку жизненного цикла; совместная работа старого и нового бинарника с новой схемой не является поддерживаемым rolling upgrade.

## Проверки

- Go-тесты с PostgreSQL, `-race`, `go vet`.
- Регрессии F1/F2; серверная обработка подтверждений.
- Удаление во время LLM и отправки Telegram; отказ от повторного исполнения после восстановления.
- Отзыв ключей POST, очистка чужого старого snapshot при переносе расхода удаляемому участнику, версии удаления/восстановления.
- 18 тестов фронтенда, ESLint, Prettier, сборка TypeScript/Vite.
- Браузерная приёмка: конфликт PUT, потерянный ответ, подтверждение/отмена удаления и восстановление доступа, прежние сценарии интерфейса.
- Compose smoke test с CRUD и новым API управления участниками.
- `govulncheck` и `npm audit --audit-level=high`: уязвимости не обнаружены при локальной проверке.

Внешние Telegram/LLM end-to-end не запускались; используются тестовый Telegram API и управляемые планировщики. Обновлённый промпт требует отдельного live-прогона выбранной модели.

## Gitflow

Подготовка релиза: `release/0.2.0` → `main`, тег `v0.2.0`, затем обратное слияние релиза в `develop`.
