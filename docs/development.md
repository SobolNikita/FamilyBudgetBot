# Разработка и проверки

[← README](../README.md)

Команды выполняются из корня репозитория, кроме блоков с явным переходом в web. Конфигурация контейнеров и эксплуатационные команды — в [отдельном документе](operations.md).

## Локальная разработка

Нужны Go 1.27.2+, Node.js 24 и PostgreSQL. Для запуска вне Docker задайте переменные окружения из `.env.example`, а также `DATABASE_URL=postgres://user:password@localhost:5432/family_expenses?sslmode=disable`. Go-приложение само `.env` не читает. При специальных символах в пароле URL кодируется стандартным способом; Compose передаёт пароль отдельно через `PGPASSWORD`.

```sh
go run ./cmd/migrate
go run ./cmd/app
```

В другом терминале:

```sh
cd web
npm ci
npm run dev
```

Vite проксирует `/api` на Go-сервис по адресу `http://localhost:8080`. Для статической сборки выполните `npm run build`, после чего панель раздаёт сам Go-сервис.

```sh
go test ./...
go vet ./cmd/... ./internal/...
cd web
npm test
npm run build
```

Интеграционные тесты включаются переменной `TEST_DATABASE_URL`, указывающей на тестовую PostgreSQL. Они создают изолированную схему и удаляют её после теста. Без переменной эти тесты явно пропускаются. Проверяются SQL-миграции, регистрация и её повторы, точность сумм, фильтры дат, изоляция участников, конфликты версий, очередь, дедупликация и откат транзакции.

### Приёмка естественного языка

Обычные Go-тесты не обращаются к LLM. Отдельный набор из 18 синтетических примеров проверяет выбранную реальную модель: фразы из ТЗ, «вчера» на границе февраля високосного года, уточнение суммы, неоднозначное удаление, несколько покупок, отказ в чужих расходах, инструкции внутри комментария, продолжение списка после сокращения истории и поиск фастфуда с недавними расходами и без них.

Из корня проекта с настроенными `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` в `.env`:

```sh
node --env-file=.env scripts/check-llm.mjs
```

Нужны Go и Node.js 24. Скрипт вызывает только LLM с вымышленными данными; Telegram и база приложения не используются. Результаты содержат дату, модель, endpoint, хеш системного промпта, ожидаемые и фактические действия. Отчёт сохраняется в `.cache/llm-eval.json`; путь можно задать через `LLM_EVAL_REPORT`. Ключ не записывается в отчёт. Один прогон делает максимум 18 вызовов, с лимитом 30 секунд на вызов и пяти минут на набор. Автоматических повторов нет: ошибка провайдера останавливает дальнейшие вызовы, не превращая пропущенные примеры в успешные.

Набор проверяет семантику предложенных действий; серверное выполнение и изоляцию проверяют обычные тесты. Для текущего месяца/недели допускается верхняя граница «сегодня» либо конец календарного периода. При неоднозначном удалении допустимы уточняющий вопрос или список кандидатов с соответствующим поиском; выбор произвольной записи для удаления не допускается. Один успешный прогон не гарантирует все будущие ответы модели. При изменении модели или промпта приёмку следует повторить; платные вызовы в обычный CI не включены.

Проверка 18 октября 2026 года на `gemini-3.1-flash-lite`: **16 из 16 примеров прошли**. [Полный результат с входами, действиями и хешем промпта](evaluations/llm-2026-10-18.json). По результатам приёмки уточнены инструкции: просьба показать записи не должна заменяться сводкой, а неизвестная сумма требует вопроса, без попытки записать `?` как цену.

Этот отчёт относится к сохранённому в нём хешу промпта. После добавления дат исторических реплик промпт изменён; прежние 16/16 не являются live-проверкой новой версии. Обычные тесты, проверки PostgreSQL и управляемые планировщики не заменяют повторную приёмку выбранной реальной модели.

### Форматирование и линтеры

Prettier форматирует фронтенд, JavaScript-скрипты и CI-конфигурацию; ESLint проверяет TypeScript/JavaScript в `web`, включая правила вызова React Hooks и зависимости эффектов. Форматирование и проверка логики разделены через `eslint-config-prettier`. Версии инструментов закреплены в `web/package.json` и lock-файле. Настройки отступов и переводов строк для редакторов находятся в `.editorconfig`; `.gitattributes` сохраняет LF при получении файлов из Git и на Windows.

Из корня проекта:

```sh
node scripts/go-format.mjs --write
go vet ./...
npm --prefix web run format
npm --prefix web run lint
```

Проверки без изменения файлов: `node scripts/go-format.mjs` и `npm --prefix web run format:check`. Для автоматического исправления поддерживаемых ESLint ошибок: `npm --prefix web run lint:fix`. В PowerShell при блокировке `npm.ps1` используйте `npm.cmd`. Автоформатирование при сохранении зависит от редактора: используйте расширение Prettier для фронтенда и Go с форматтером `gofmt` для Go.

CI в `.github/workflows/ci.yml` выполняется на push и pull request: проверяет `gofmt`, запускает `go vet`, Go-тесты с race detector и отдельной PostgreSQL, govulncheck, npm audit, Prettier, ESLint, тесты фронтенда, сборку и браузерную приёмку. Отдельное задание собирает и запускает приложение через Compose, проверяет миграции, статику, health endpoints, CRUD, фильтры, конфликт версий и повтор запроса после удаления записи. При нарушении форматирования, ошибках линтера или срабатывании проверок уязвимостей проверка завершается неуспешно. Чтобы запретить слияние при ошибках, в настройках GitHub нужно сделать задания CI обязательными для защищённой ветки.

Проверка интерфейса в headless Chrome: после сборки фронтенда выполните из корня `node scripts/check-web.mjs`. Скрипт использует только тестовые API на порту 5189, проверяет экраны 320–1440 px, формы и пагинацию, сохраняет снимки в `.cache`. Нужны свободные порты 5189 и 9239; Chrome по умолчанию ищется в стандартной папке Windows, другой путь задаётся через `CHROME_PATH`. Рабочая БД и обычный профиль браузера не используются.

Локальная проверка установки из контейнеров: `node scripts/check-compose.mjs`. Требуются Docker Compose v2 и Node.js 24. Скрипт использует основной `compose.yaml`, создаёт случайное имя проекта, отдельный volume и образ, временный env-файл без рабочих ключей и случайный локальный HTTP-порт. Бот выключен. В конце удаляется только созданный тестовый проект вместе с его данными и тестовым тегом образа. Рабочая `.env` не читается. Переменные `APP_ENV_FILE` и `APP_IMAGE` позволяют этой проверке переопределить env-файл и образ; при обычном запуске по-прежнему используются `.env` и `family-expenses:local`.

## Тестовые страницы расходов

Используйте отдельную тестовую БД: скрипт создаёт настоящие расходы.

`scripts/seed-pagination.sql` добавляет 240 расходов существующему участнику (12 страниц по 20 записей). Передайте в `psql` параметры `-v user_id=ID` и `-v spent_at=YYYY-MM-DD`. Комментарии помечены `[pagination-test-v1]`; повторный запуск для того же участника не дублирует записи. Это настоящие записи в выбранной БД: они учитываются в отчётах. Для удаления только этого набора используйте `DELETE FROM expenses WHERE user_id = ID AND comment ~ '^\[pagination-test-v1\] [0-9]{3}$';`, подставив ID участника.

## Gitflow и коммиты

Сообщения коммитов в формате Conventional Commits: `feat: add expense management`, `fix: prevent duplicate telegram expenses`, `docs: describe deployment`, `test: cover expense isolation`, `chore: update dependencies`.

Ветки: `main` — основная версия, `develop` — интеграция изменений, `feature/*` — новая функциональность, `release/*` — подготовка версии, `hotfix/*` — срочные исправления основной версии.

Начальная история реконструирована из уже существовавших файлов: коммиты группируют готовую работу по подсистемам. Даты коммитов отражают инициализацию репозитория, а не первоначальное время разработки.
